## 一、模块目标

把五本书里有原文依据、但游戏知识层尚未建卡的「新咖啡」做成知识卡：先挂进现行旧线（`story/chapters` 五章）在游戏中可玩到；用户新主线（`story/new-game` 七章七杯）上线时，同一批卡可直接被新线引用——一次生产，两条故事线共用。

## 三、功能点

**F1 新知识卡（素材为准，不得编造）**

- 拟覆盖（新线七杯中有书源者）：冰滴、冷萃、美式、摩卡、卡布奇诺——逐杯对 b2/b3/b4 勘察后定精确卡单，每杯 1~3 张，总量以设计勘察为准。
- 每卡满足既有 schema（id / title 2-20 字 / category 六枚举 / plain_explanation 10-120 字 / source_book / source_chapter / source_quote ≤200 字 / confidence / related_stages）；medium 必带 inference_note；source_quote 必须为书源原文摘录且可在 `content/raw` 对应文本中定位。
- 黑糖拿铁、余温：已知无书源（b2/b3/b4 实测 0 命中；b1/b5 未 OCR）⇒ 本批不出卡，缺口入设计档缺口表 + 台账（供新线接入批次处置）。

**F2 旧线挂接（只增不改）**

- 把新卡挂进 `story/chapters` 五章既有挂点（三形式中语义相符者）：仅允许追加——`knowledge_brief[]` 追加元素、既有 `choices[]` 补 `knowledge_id` 字段、`reward.unlock_knowledge[]` 追加元素。
- 禁止改动：叙述/标题/选项文本/effects/flags/next_stage/阶段结构等一切剧情与逻辑字段；不得删改既有知识引用；不得重排文件。改动清单逐文件逐锚点列入设计档（含 §八 合规处理说明）。
- 语义不相符的挂点禁止硬塞；某杯无恰当挂点 ⇒ 记入设计档缺口表（新线接入承接），不停工。
- 若发现与 §八 或契约存在真实冲突（无法既合规又完成挂接）⇒ 设计停下上报，不得自行改口径。

**F3 对照与接入表**

- `content/关卡知识库对照.md`（手工同步）与 `content/关卡知识库.html`（`npm run kb` 重生成）随卡同步，计数与实际一致。
- 设计档输出「新线七杯 → 卡 ID」接入对照表（含无卡杯的缺口标注），供 story/new-game 接入批次直接取用。
- 新卡 related_stages 是否回填由设计按契约定（契约允许留空、由故事轨反向补；若回填须与挂点一致）。

**F4 号段与落盘**

- 新卡按契约落书2 号段（200–239）与相应分片文件（书2 前段分片尚未存在，文件名与号段由设计按契约确定）；书3/书4 若产出新卡，用其号段内空闲号并按分片规则落盘。
- `contracts/**` 为冻结区：本批目标零字段变更；若确需号段登记等程序性变更，按契约变更记录登记一行（设计档明示）。

## 四、边界（本批不做）

- 不做新饮品数据（`content/drinks/**`）；不动 `game/**`、`index.html` 与工程面。
- 不写剧情文本；不触碰 `story/new-game/**`（用户手写包，只读）；对 `story/chapters/**` 仅做 F2 所述知识字段追加。
- 不做书1/书5 知识卡（OCR 前置 = 台账 #12）；不扩到七杯之外的饮品（康宝蓝/玛奇朵/维也纳等经典款不入本批）。
- 不改 `contracts` 字段与 schema；不改 story 结构字段。
- 不推送、不部署（沿用 b01 §4 发版口径）。

- **V1** `npm run validate` error=0；新增引用不产生新 warning（引用的卡 ID 全部已产出）。
- **V2** `npm test` 全绿，无回归。
