## 1. 方案与理由

### 1.0 三条全局口径

1. **契约零变更（X1 / 决策 L）**：所有新模式状态走**侧车存储**（设备级或档位级 localStorage 键），`PlayerSave` 与 `contracts/**` 一字不改，不新增 `Effects` / `PlayerSave` 字段。
2. **显式穿线，不读全局**：经济口径等环境依赖以**显式参数**传入纯函数（`Economy` / `ServeOptions`），函数内部不读 `localStorage`、不读模块级开关；既方便断言，也保住现有测试的口径（`game/src/state.ts:122` 起原有调用签名缺省行为不变）。
3. **逻辑与存储分离**：判定 / 生成 / 评级 / 编解码全部为纯函数（依赖全在参数里）；`localStorage` 读写只出现在薄封装；React 组件只做展示与事件。

存储键总表（全部 `localStorage`；沿用键语义不变）：

| 键 | 归属 | 内容 | 本批 |
|---|---|---|---|
| `yuwen-cafe-save-v2:<profileId>` | 档位 | `PlayerSave` | 沿用（结构不变） |
| `yuwen-cafe-profiles-v1` / `-active-v1` / `-save-v1` | 设备 | 档位清单 / 当前档 / v1 旧档 | 沿用 |
| `yuwen-cafe-settings-v1` | 设备 | `{ relaxedEconomy: boolean }` | 新增（M2） |
| `yuwen-cafe-business-v1:<profileId>` | 档位 | 营业档案 `BusinessRecord` | 新增（M3） |
| `yuwen-cafe-recipes-v1` | 设备 | 配方库 `Recipe[]` | 新增（M7） |
| `yuwen-cafe-feedback-v1` | 设备 | 本机反馈列表 `FeedbackItem[]` | 新增（M6） |

读写全部 `try/catch` 降级（沿用 `game/src/state.ts:233-258` 的 `store` / `readJson` / `writeJson` 手法，抽成共享小工具 `game/src/store.ts`，`state.ts` 与本批各存储薄层一并自它导入）；node 环境（无 `localStorage`）静默降级为「本局可玩、存不下」。

### M1 进度安全：买豆 + 应急豆（P0）

**做法**

1. **买豆**：`state.ts` 新增 `buyBean(save, beanId, eco?)`。价格 = `bean.purchase_price`（整袋价），到货 `stateKeys.economy.bean_portions_per_bag`（= 20）份。
   落地走一次 `applyEffects(save, { money: -price, inventory: { [beanId]: 20 } }, eco)`：现金、库存、当日流水同源更新；库存为增量，不记 `wasted`。
2. **进货屏**：新增 view `'purchase'` 与 `Purchase.tsx`——列全部 30 支豆（名称 / 产地 / 处理法 / 烘焙度 / 风味标签 / 进价 / 「这袋能出什么」），按进价排序，买不起的按钮禁用并标注差额；
   顶部一行 `现在能出杯的豆：N 支`，为 0 时提示「应急豆可用」。
   入口两处：仓库屏按钮（`game/src/App.tsx:423` 起 `Storage`）与吧台空态（`game/src/App.tsx:515-522`）。
3. **应急豆**：`state.ts` 导出 `EMERGENCY_BEAN_ID = 'bean-emergency'` 与常量 `EMERGENCY_BEAN`（虚拟豆：`usable_drinks` = 全部饮品 id、`purchase_price` 0、`flavor_tags: []`、`source_chapter: '游戏机制'`，**不进 `content/**`**）。
   判定 `canBrewAnything(save)` = 存在「有库存且 `brewableWith` 非空」的豆；为 `false` 时，吧台与客人关的空态显示应急豆卡与「去进货」。
4. **应急出杯**：`serveDrink` 识别应急豆 id → 成本 0、库存判定与 `inventory` 写入整体跳过（无限份）、收入照记（`incomeOverride` 或 `drink.price`）；
   出杯流程、级联判定与正常豆完全一致（M8 交互照走）。
5. **自愈闭合**：0 豆 0 现金 + 宽松模式（M2 默认开）⇒ 应急出杯 → 按 `drink.price` 进账 → 攒够最便宜一支豆的整袋价即可进货 ⇒ 不需删档、不改 story，卡死在机制上不成立。
   宽松模式关闭时同样自愈（应急出杯 0 成本、有收入），只是攒得慢。

**理由**：`story/**` 的 `effects` 从不写 `inventory`（全量 grep 0 命中），补豆只能是游戏轨机制。应急豆用「零成本 + 无限份 + 正常收入」把死锁转成慢速推进，比动剧情或赠送库存更可控。
买豆并入 `applyEffects` 的记账路径，避免另开一条账。

### M2 经济放宽：金钱无限（开关，默认开）

**做法**

1. **开关**：`settings.ts` 的 `loadSettings` / `saveSettings`；缺省 `{ relaxedEconomy: true }`（决策 A：开关式；决策 B：全局设置、与存档解耦、旧档自动生效）。
2. **穿线**：`state.ts` 导出 `interface Economy { unlimited: boolean }`；`applyEffects(save, effects, eco?)`、`buyUpgrade(save, id, eco?)`、`buyBean(save, beanId, eco?)`、`serveDrink(save, drink, beanId, opts?)` 增加可选末参，缺省 = 真实经济。
3. **语义**：`eco.unlimited === true` 时，`effects.money` 的**负值免扣**（余额不动、不产生现金变化文案），**正值照记**；
   `today.revenue` / `today.cost` 一律按**原始金额**记账（流水是账本，不是余额）。
4. **显示**：`displayMoney(save, unlimited)` → `'∞'` / `String(save.money)`；HUD（`game/src/App.tsx:176`）、菜单黑板现金行（`game/src/App.tsx:478`）、进货屏、结算页统一走它。
5. **界面**：店内页新增「店务」一栏，含宽松模式开关（`role="switch"`，切换即 `saveSettings` + 立即生效）。

**理由**：需求指定「开关式、默认开、随时可关」。把 `unlimited` 做成显式参数而不是读全局，是为了让两种口径下的行为都能被直接断言，也让宽松模式不污染 `state.ts` 的既有语义（现有测试零改动）。

### M8 冲煮交互：出杯手感

**做法**：`brew.ts`（纯函数）+ `BrewInteraction.tsx`（组件），插在「选豆选品之后、出杯之前」。

1. **参数派生** `deriveBrewParams(bean, drink, override?)`：

| 项 | 来源 | 取值 |
|---|---|---|
| 水温区间 `tempC` | `bean.roast_level` | 浅烘 [92,94] · 中浅烘 [90,93] · 中烘 [88,91] · 中深烘 [86,89] · 深烘 [85,88] |
| 研磨 `grind` | `drink.method` | 浓缩 细 · 奶咖 细 · 手冲 中细 · 滴滤 中 |
| 粉量 `doseG` | `drink.method` | 浓缩 18 · 奶咖 18 · 手冲 15 · 滴滤 22 |
| 水量 `waterMl` | `drink.method` | 浓缩 36 · 奶咖 36（另 180ml 牛奶）· 手冲 240 · 滴滤 360 |
| 时长 `timeS` | `drink.method` | 浓缩 27 · 奶咖 25 · 手冲 150 · 滴滤 210 |
| 提示 `notes` | 烘焙度 + method | 模板生成 2~3 条，如深烘「水温别冲太高，苦味容易出来」、手冲「闷蒸 30 秒再接注水」 |

`override`（来自 M7 配方预设）按字段覆盖派生值；非法值忽略并回落派生值，使「按配方来一杯」的显示与判定都可复现。

2. **交互映射** `interactionFor(method)`——覆盖契约中全部 4 种 method（数据现有 3 种：浓缩 / 手冲 / 奶咖；滴滤为第 4 种，预留映射）：

| method | 形态 | 轮数 | 满量程 / 节拍 | 单轮超时 | 好评容差 |
|---|---|---|---|---|---|
| 浓缩 | `hold` 压粉 | 1 | 3500ms | 4000ms | 0.12 |
| 奶咖 | `hold` 打发 | 1 | 4200ms | 4500ms | 0.14 |
| 手冲 | `taps` 分段注水 | 3 | 1600ms / 拍 | 4000ms | 0.15 |
| 滴滤 | `hold` 注水 | 1 | 3000ms | 3500ms | 0.15 |

最坏时长：手冲 3×4s = 12s、奶咖 4.5s、浓缩 4s，全部 ≤ 15s（M8.3）。

3. **评级**：单轮 `d = |v - 0.5|` → `d ≤ band` 好 / `d ≤ 2×band` 一般 / 否则失误；多轮取均值（好 = 1、一般 = 0.5、失误 = 0）→ `≥ 0.75` 好、`≥ 0.42` 一般、否则失误。
   超时或未操作 → 自动取值 `AUTO_VALUE = 0.72`（对四种 band 都落「一般」区间），即「没动手也照样出杯」（决策 I：失败也出杯、不扣资源）。
4. **静态降级**：`prefers-reduced-motion: reduce`（或 pointer 能力缺失）→ 静态「参数三选一」（对 / 差一档 / 差两档），正解由**同一份** `BrewParams` 派生，评级同走 `gradeRound` 家族。
5. **结果去向**：评级 → 满意度（主线 `GRADE_SATISFACTION = { 好: 3, 一般: 1, 失误: 0 }`）；自由营业由 `rateOrder` 并入星级（M3）。

**理由**：参数派生与判定的**耦合点**只放在「提示文案 + 静态降级题 + 配方复现」三处，不给判定挂伪物理（例如按水温差平移好评带）——那只会制造不可解释的手感。
判定只依赖方法与输入，因此配方预设天然可复现（同参数 ⇒ 同题面 ⇒ 同判定）。

### M3 无尽营业：通关后「自由营业」日循环

**做法**：`business.ts`（纯函数 + 薄存储）+ `BusinessView.tsx`；入口 = 店内页「门店」区（通关后可点，未通关置灰标注）。

1. **触发**：`isStoryComplete(save)` = `!save.current_stage && save.completed_stages.length >= stages.length`（`stages` 取自 loader）。
   末关后的空文案面板（`game/src/App.tsx:219-224`）替换为「开门营业」入口 + 一句「故事走完了，店还开着。」
2. **日循环状态机** `BusinessRecord`：`phase: 'open' | 'serving' | 'settled'`（日始 / 接单中 / 今日已收工）；`day`（营业第 N 天，从 1 起）、`orders`（今日日计划，入场即生成并落盘）、`served`、`stars`、`income`、`usedBeans`、`planSeed`。
3. **客流**：`dayGuestCount(reputation) = min(5, 2 + floor(reputation / 25))`（30 → 3、50 → 4、75 → 5）；每位客人出杯后 `energy -1`，`energy` 归零则当日结束（余下客人「改天再来」）。
   口碑合法范围由契约钉死 `[0, 100]`（`contracts/state-keys.json` 的 `reputation`，`applyEffects` 钳制）⇒ 客流**下限恒为 2**（`rep = 0` → `min(5, 2 + 0) = 2`），不存在负口碑、零客流或日循环停摆。
4. **订单生成（确定性、可测）**：`seed = day * 7919 + round(reputation)`，LCG 取数——
   客人 = 非玩家角色池（6 位）；饮品 = `availableDrinks(save)` 中「至少一支豆能做」的一款；
   风味偏好 = 「能做该饮品的豆的 `flavor_tags` 并集」中取 1 个；`reputation ≥ 60` 时取 2 个，且要求该组合同时存在于某一支豆（找不到就退回 1 个）。
   订单文案模板：「{客人}：想喝{饮品}——{偏好1}、{偏好2}」。
5. **三段判定 → 星级**：饮品对上 +1；豆全中偏好 +1 / 部分 +0.5；手法 好 +1 / 一般 +0.5 / 失误 0。
   合计 `≥ 2.5` → 3★、`≥ 1.5` → 2★、否则 1★。判定附 1~3 行数据依据（如「{豆名} 的 flavor_tags 命中『低酸』」/「这支豆没有『低酸』，它是 花香／柑橘」）。
6. **结算**：收入 = `round(drink.price × [1.0, 1.2, 1.5][stars - 1])`；`satisfaction_today += stars × 3`；`reputation += { 3: +1, 2: 0, 1: -1 }`；`trust[客人] += stars - 1`（仅 `stateKeys.trust.characters` 内的 5 位具名角色）。
   以上全部经**一次** `serveDrink(..., { eco, incomeOverride, extraEffects })` 落地（单一写入点，避免重复计账）。
7. **日终**：复用 `closeDay` + 现有结算页 `Settlement`，加 `dayLabel = '营业第 N 天'`；结算页「回到店里」→ 营业页，`phase` 回 `open`、`day += 1`。主线结算页不传 `dayLabel`，保持原样。
8. **成长轴**：口碑（影响客流与偏好个数）、熟客（`trust` 展示）、豆种图鉴（`usedBeans`，主线与自由营业每次成功出杯都记：`recordUsedBean(profileId, beanId)`）、配方图鉴（M7 库计数）。
9. **软处理**：没满足偏好只是少星少收；无硬失败、无 Game Over；缺豆缺钱由 M1 机制兜底（应急豆永不缺席）。

**理由**：日循环全部由现有数据（豆标签、饮品、角色）驱动、零新增剧情文本，符合 M3 边界；种子取自 `day + reputation` 且日计划入场即固化，使「同一天怎么玩都一致」且测试可重放。

### M5 存档迁移：存档码导出 / 导入 + 完成态显示

**做法**：`share.ts`（M7 复用）+ 首页档位行扩展。

1. **码格式**：`前缀 + 校验段 + '.' + base64url(JSON)`
   - 存档码前缀 `YWCAFE-SAVE-1.`，配方码前缀 `YWCAFE-RECIPE-1.`；校验段 = FNV-1a32（对 base64url 段的 UTF-8 字节）→ 8 位小写 hex。
   - base64url 按 0x8000 分块 `String.fromCharCode` 拼接（避免大存档爆栈）；中文安全（先 `TextEncoder` 转字节再编码）。
2. **导出**：档位行「导出」→ 生成码 → 面板内只读 `textarea`（可手动全选）+ 三键：复制 / 系统分享（`navigator.share`，不可用回落复制）/ 下载 `.txt`（`Blob` + `a[download]`）。
   载荷 = `{ v: 1, app: '0.2.0', profileName, exportedAt, save, business }`（带上营业档案，跨设备接着营业）；`business` 为 `null` / `undefined` 时**整键省略**（不编码 `business: null`）。
   - `business` 为**可选**字段：旧版码或缺失该字段的码导入时**优雅降级**——新档位的营业档案从「营业第 1 天」起算，不报错、不阻断导入。
   - 该载荷**不改** `contracts/**`，也不改 `PlayerSave` 结构：`business` 是本机侧车档案被搬进包络，不落进存档 JSON（`save` 字段仍只是 `PlayerSave` 本身）。
3. **导入**：首页底部「导入存档码」→ 粘贴 → `planImport(code, 现有档位名列表)` → 预览（档位名 / 章节 / 已完成关数 / 现金 / 营业天数）→「确认导入」→ **新建档位**（不覆盖现有档；重名自动加 `（2）`、`（3）`…）。
   非法码逐类明确报错：前缀不符「这不是存档码」/ 校验不过「校验不通过，可能被改动或复制缺了一段」/ 解码失败「这段码读不出来」/ 结构不符「码里的存档结构不认识」。
4. **完成态显示**：`profileProgressLabel(save, businessDay?)`——
   未通关 → `第 N 章 · 进度 n/50 · 现金 X · 知识卡 Y 张`；通关 → `已通关 · 自由营业[第 N 天] · 现金 X · 知识卡 Y 张`。
   首页档位行改用它（一并修掉 `game/src/App.tsx:291` 的「第章」缺陷）。

**理由**：编码只在存档外层包络，存档结构与 `contracts` 保持冻结（X1 / X3）；校验段与载荷分离，使「码被截断」与「码被改动」能给出不同提示；「导入必新建档位」是需求硬约束，落成纯函数 `planImport` 后无需 DOM 即可测。

### M7 配方共创：做法提交与收录

**做法**：`recipes.ts` + `RecipesPanel.tsx`，复用 M5 的编解码与 M8 的参数结构。

1. **数据**：`Recipe = { id, name, author, beanId | '', drinkId, params: Partial<BrewParams>, note, createdAt }`；`id = fnv1a(canonical)`（canonical 不含 `createdAt`）⇒ id 即去重键。
2. **编辑器**：名称（≤ 24 字）、署名（≤ 12 字，可空 → 显示「匿名」）、豆（含「任意」）、饮品、参数（按饮品 method 呈现：粉量 / 水量 / 水温 / 研磨 / 时长）、风味笔记（≤ 120 字）；
   「刚从吧台做的那杯」→ 一键填入（本局内存草稿：出杯成功即记 `lastBrew = { beanId, drinkId, params }`，刷新后自然失效，不额外落盘）。
3. **提交码**：`encodeRecipe` → `YWCAFE-RECIPE-1.<校验段>.<base64url>`；复制 / 分享 / 下载同 M5 三键。
4. **收录台**：粘贴 → `decodeRecipe` → 预览 → `addRecipe(list, recipe)`（重复 id → 「这条配方已经在库里了」；非法 → 明确 reason）。
5. **配方墙**：倒序列出（时间新在前）：名称 / 署名 / 豆（或「任意」）/ 饮品 / 参数摘要 / 风味笔记；
   按钮「按这配方来一杯」→ 去吧台，`preset = { drinkId, beanId?, params }`；配方指定的豆不在库存时给一行提示并落回「任意豆可用」，不阻塞。
6. **界面**：店内页「店务」栏入口「配方墙」；`RecipesPanel` 三段式（编辑器 / 收录台 / 配方墙）。

**理由**：配方参数直接复用 `BrewParams`（`Partial` 覆盖），使「按这配方来一杯」无需第二套语义；库为本机存储、传播靠码（决策 F；云共享属后续批）。

### M6 问题反馈：零后端窗口

### M10 档位行文案：进度解析失败的展示（2026-09-30 设计评审发现 F6 · 批次 b04）

> 坐标口径：本批实测值（2026-09-30）；行数为 `wc -l` 数法。

**问题陈述**

档位行文案 `profileProgressLabel`（`game/src/share.ts:159-164`）把章节号解析成 `Number(String(save.current_chapter).replace(/\D/g, '')) || 0`（`:162`）：读不出数字即落 `0`，档位行于是渲染「第 0 章」——一个并不存在的章节号，是面向玩家的假信息（`game/src/App.tsx:732` 存档列表、`:835` 导入预览两处都直接展示该函数返回值）。同一正则还制造第二个假号：小数 `chapter-1.5` 被剥成 `15` ⇒ 「第 15 章」。

**做法**

1. **解析改严格规范式**：新增局部纯函数 `chapterNumberOf(raw): number | null`，仅在 trim 后匹配 `/^chapter-(\d+)$/` 且为安全正整数（`Number.isSafeInteger` 且 ≥ 1）时返回该数，否则返回 `null`：

   ```ts
   function chapterNumberOf(raw: unknown): number | null {
     const m = /^chapter-(\d+)$/.exec(String(raw ?? '').trim());
     if (!m) return null;
     const n = Number(m[1]);
     return Number.isSafeInteger(n) && n > 0 ? n : null;
   }
   ```

   唯一合法产出形 = `chapter-01`…`chapter-05`（产出者 `game/src/state.ts:99` / `:301`，取自 `story/chapters/*.json` 的 `chapter` 字段）⇒ 1…5；空串 / 纯非数字 / `0` / 负数 / 小数 / 超长数字串（非安全整数）一律 ⇒ `null`（取值域与判定见下表）。
2. **失败态形态 = 省略章号段**：`chapter === null` 时输出 `进度 n/50 · 现金 … · 知识卡 … 张`（丢掉读不出的章号段，其余真实信息照常）；解析成功时输出与今日逐字相同的 `第 N 章 · 进度 n/50 · …`：

   ```ts
   const chapter = chapterNumberOf(save.current_chapter);
   const progress = `进度 ${save.completed_stages.length}/${stages.length}`;
   return chapter === null ? `${progress} · ${tail}` : `第 ${chapter} 章 · ${progress} · ${tail}`;
   ```
3. **通关分支与正常解析分支文案不变**（回归红线）：`:161` 通关分支与合法解析下的「第 N 章 · 进度 n/50 · …」逐字保持；对合法存档，新实现输出与旧实现完全一致。

**取值域与判定（哪些算「解析失败」）**

**校验口径 = 格式校验（不查章节内容轴存在性）**：本批只判 `current_chapter` 能否读出**格式合法且数值可信**的章号（严格规范式 + 安全整数），不校验该章号在 `story/chapters/**` 内容轴是否真实存在——章节内容轴本批零改动，且越界 / 超长值本属损坏档，按格式规则原样呈现更便于识别。

| `current_chapter` 取值 | 判定 | 理由 |
|---|---|---|
| `chapter-01`…`chapter-05`（规范式） | 成功 ⇒ 1…5 | 唯一合法产出形（`state.ts` + `story/chapters`） |
| `chapter-06` 等超范围规范式（内容轴无此章） | 成功 ⇒ 6 ⇒ 原样显示「第 6 章」 | 本批只做格式校验，不查内容轴是否存在该章（章节存在性属 `story/chapters/**`，本批零改动） |
| 空串 `''` / 全空白 | 失败 ⇒ 省略 | 无章节信息 |
| 纯非数字（`第一章` / `abc`） | 失败 ⇒ 省略 | 无正整数可读 |
| `0` / `chapter-00` | 失败 ⇒ 省略 | 章节号从 1 起，`0` 不是真实章节（旧逻辑正是在此渲染「第 0 章」） |
| 负数（`-1` / `chapter--1`） | 失败 ⇒ 省略 | 旧的 `\D` 剥离会把它读成 `1`（假号） |
| 小数（`1.5` / `chapter-1.5`） | 失败 ⇒ 省略 | 旧的 `\D` 剥离会把小数点当噪声删掉，读成 `15`（假号） |
| 超长 / 非有限 / 非安全整数（`chapter-99999999999999999999`） | 失败 ⇒ 省略 | 数值转换结果越出安全整数范围（不可信），不得当章号展示 |

**「解析失败」≠「未开始游玩」**：本情形的判据只有 `current_chapter` 能否读出章号，与存档是否真的零进度是两件事——`completed_stages` 已有进度的存档（跨版本导入 / 字段损坏）同样可能读不出章号。「未开始游玩」若要展示，须由真实进度字段（`completed_stages` / `current_stage`）判定，不从「章号读不出」反推；本批不新增「未开始」态（那属新语义，超出 F6 面）。

## 7. 边界（本设计不做）

- 不改 `story/**`、`content/**`、`contracts/**`（含 `state-keys.json`）；不新增 `PlayerSave` / `Effects` 字段。
- 不做账号 / 云同步 / 服务端 / 排行榜 / 遥测；反馈不自动上传，配方传播靠码。
- 不做原生壳（apk / ipa）；不做自定义域名；不动 GitHub Pages 工作流；本批不推送、不部署（决策 K）。
- 不做物理模拟、不做多轮进阶冲煮、不设硬失败；冲煮交互不扣资源、不阻挡出杯。
- 不做赊账 / 贷款 / 库存赠送：0 豆 0 现金的出路是「应急豆出杯 → 攒钱 → 买豆」。
- 不做无尽营业的目标 / 失败条件 / 排名；不做配方库的全体发布与云收录（后续批）。
- 不做组件级单测（node 环境无 DOM）；不做端到端浏览器测试；UI 由手工走查 + 结构机检覆盖。
- 不做多语言、不做主题换肤、不做音效。
- M9 不改任何既有入口与信息架构（底栏 / 店名按钮 / 「换档」/ 各视图既有返回全部原样）；不引路由库、不接管浏览器返回键、不做手势返回；不做滚动位置记忆（要求即「不保留」）。
- M9 的组件级断言为「直调函数取元素树」，不渲染 DOM、不引 jsdom（承 D13 口径）。
